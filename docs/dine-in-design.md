# 店内専用料理システム — 初期基本設計 (Draft v0.1)

## 目的
FiveMの店舗に訪問し、着席して時間をかけて食事する体験を提供する。持ち運べる消費アイテムとの差別化として、高い満腹度等の回復を設計する。

## 基本ルール（提案）
- 店内専用料理は原則インベントリアイテムとして発行しない。
- 設定済み店舗と指定座席でのみ注文・食事できる。
- 店舗ごとに料理・価格・食事時間・満腹度/水分回復量を設定可能。
- 通常飲食アイテムの目安：3–5秒、満腹度20–35%。
- 店内専用料理の目安：20–40秒、満腹度50–80%。
- これらの数値はすべて初期バランスの仮案で、サーバー環境に合わせて変更する。

## 体験フロー（設計案）
1. 店舗内の注文ポイント、または座席メニューにアクセス。
2. 料理・価格・効果・食事時間を表示し注文。
3. 料理を席に提供（初期MVPでは表示・状態のみでも可）。
4. プレイヤーが席で食事を開始。
5. 食事時間経過後に回復。途中キャンセル時の回復・返金ポリシーは別途決定。
6. 提供状態と席の利用状態を終了処理でクリア。

## MVP範囲
- 店舗・座席・メニュー・料理効果のConfig設定
- 座席位置と店舗範囲のサーバー側検証
- 注文・提供・食事開始・完了の状態管理
- 進捗バーとキャンセル処理
- サーバー側での支払い・回復の確定
- 二重注文、連打、席の重複、途中退出、切断に対する整合性対策

## モジュール境界
初期候補名：`ptech_restia_dining`。
注文管理モジュール・調理モジュール・レジモジュールは必須依存にしない。必要時に任意連携できるよう、公開APIを検討する。

## 提供方式（確定方針）
店舗ごとに `serviceMode` を設定し、有人提供と自動提供を切り替える。

- `staff`: 店員による提供。権限を持つプレイヤーが注文を確認し、提供操作を行うまで「提供済み」にならない。
- `auto`: 自動提供。注文確定後に設定された準備時間を経て、サーバー側で「提供済み」に遷移する。
- どちらの方式も提供後の着席・食事開始・進捗・回復処理を共通化する。
- 店舗ごとの設定で完結し、調理・注文・会計モジュールを必須依存にしない。
- 店員がいないときに自動提供へ切り替える機能は現時点では設けない（別途検討）。

### 提供状態
`ordered` → `preparing` → `served` → `eating` → `completed`

キャンセル、切断、店舗外移動時は別途キャンセル／失効状態へ遷移。自動方式のタイマーや有人方式の提供操作はサーバーで検証し、二重提供・二重回復を防ぐ。
